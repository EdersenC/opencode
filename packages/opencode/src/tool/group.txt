Group multiple task subagent calls into one logical result.

Use group when several subtasks share one common goal and the caller should receive one combined grouped result after every inner task finishes.

A group is a bucket of related work, a cluster of parallel lanes, and a cohort of subagents working toward the same outcome. Use it for fan-out/fan-in execution: dispatch the cohort, wait at the completion barrier, aggregate the results, then synthesize the grouped result.

Usage notes:
1. One group tool call represents one group.
2. To run multiple groups concurrently, call group multiple times in the same assistant message.
3. Each group waits for all of its inner calls before returning.
4. Group by shared objective, not by random convenience.
5. For one logical implementation bucket, put every ready related coder task in the same group calls array so they start in one go.
6. Use priority only to break ties among groups that complete at essentially the same time.
7. Use separate groups for separate workstreams.
8. Do not use group for unrelated work that should return independently unless you are intentionally creating separate grouped results.
9. Do not use group when one direct tool call or one direct task call is enough.
10. v1 supports nested task calls only.
11. Inner task calls run concurrently. Do not duplicate that work yourself.
12. Inner background tasks are not supported because group waits for foreground completion.
13. fail_fast is accepted for forward compatibility, but v1 returns all settled nested results because stopping sibling task calls early without changing task/session cleanup could lose result and cancellation accounting.
14. If a nested coder task returns `<coder_result state="blocked">`, group preserves that call as blocked in metadata and output. The caller should answer or ask the user, then redispatch only the affected task.
15. For nested coder tasks, prefer input.handoff_files for handoff READMEs, interface contracts, work-package maps, and context docs. Keep input.prompt focused on the task goal, scope, constraints, and expected return format instead of pasting large handoff documents.
16. Use group to fully leverage parallel work. If several coder tasks can start from the same contracts or handoff files, put them in the same group call instead of issuing one task, waiting, and then issuing the next.
17. Use dependency-layer groups. Run a foundation or contract group only when needed, then run every ready implementation slice in one follow-up group, then run review and verification in another group.
18. Serial task dispatch is only appropriate when a later task genuinely needs concrete output from an earlier task and written contracts are not enough to proceed safely.
19. Before creating a group, identify every ready sibling task. A group can contain many nested task calls, and all of those inner task calls start concurrently.
20. For coder groups, use the configured coder subagents/models to do the coding work. The caller should coordinate contracts, boundaries, review, and verification rather than manually implementing medium or large slices.
21. If engine, CLI, tests, docs, adapters, or UI can all code against the same handoff files, dispatch them together in one implementation group.
22. Keep nested coder prompts concise. Put large handoff documents in input.handoff_files and tell the coder which files to own, avoid, verify, and report on.
23. A group is not limited to one or two task calls. If four or five ready coder slices have non-overlapping ownership, put all four or five nested task calls in the same group.
24. Do not call a single-coder group "parallel" when other ready coder slices are waiting. Parallel work means multiple nested task calls in the same group call or multiple independent group calls in the same assistant message.
25. After a foundation task returns, do one readiness pass and launch every now-ready dependent coder slice together. Do not serially drip-feed engine, CLI, tests, and docs if the contracts let them proceed.
26. Treat calls[] as the batch. Fill it with every ready sibling task that can safely run from the same contracts, handoff files, stubs, fixtures, schemas, or public behavior.
27. If you say a phase is parallel, the group call should normally contain multiple nested task calls. A single nested task is not parallel unless there are also independent group calls in the same assistant message.
28. Do not run engine first, then CLI, then tests when CLI and tests can code against the same handoff files. Put engine, CLI, tests, docs, adapters, or UI together when ownership boundaries are clear.
29. Use descriptive group.name and calls[].name values because users see those labels while work is running.
30. Keep the user experience smooth: point coder tasks at handoff_files, keep prompts short, and avoid making the user wait through avoidable serial batches.
31. Group summaries distinguish completed, failed, aborted, and blocked calls. Treat aborted as cancelled work, not as a normal task failure.
32. Batch before narration. Decide the full ready sibling set first, then emit the group call. Do not narrate a "parallel phase" and then send only one coder when other ready slices exist.
33. If only one nested coder call is ready, use task directly unless you need group metadata, grouped blocked-result handling, or a deliberately grouped single result.
34. After any foundation or shared-contract task completes, reclassify deferred slices once and launch every now-ready coder slice in the next group instead of drip-feeding follow-up work.
35. Post-foundation anti-pattern: foundation completes, then engine runs alone, then CLI runs alone, then tests run alone. Correct pattern: once contracts and handoff files exist, put engine, CLI, tests, docs, adapters, or UI in one group when their ownership boundaries are clear.
36. If you defer a coder slice after foundation, name the concrete missing artifact that prevents it from starting from the current contracts. If there is no such artifact, include it in the current calls[] batch.

{
  "name": "implement-xyz-feature",
  "description": "Several agents implement separate ready slices of the XYZ feature and return one combined result.",
  "priority": "high",
  "calls": [
    {
      "tool": "task",
      "name": "xyz-interface",
      "description": "Implement the public interface for XYZ.",
      "input": {
        "description": "Implement XYZ interface",
        "subagent_type": "general",
        "handoff_files": [
          "docs/orchestration/xyz/contracts.md"
        ],
        "prompt": "Implement the public TypeScript interface for XYZ. Keep the implementation minimal and type-safe. Return files changed, important decisions, and remaining risks."
      }
    },
    {
      "tool": "task",
      "name": "xyz-runtime",
      "description": "Implement the runtime behavior for XYZ.",
      "input": {
        "description": "Implement XYZ runtime",
        "subagent_type": "general",
        "prompt": "Implement the runtime behavior for XYZ using the interface created by the other task. Return files changed, important decisions, and remaining risks."
      }
    },
    {
      "tool": "task",
      "name": "xyz-cli",
      "description": "Implement the CLI surface for XYZ against the shared contract.",
      "input": {
        "description": "Implement XYZ CLI",
        "subagent_type": "coder",

          "docs/orchestration/xyz/contracts.md",
          "docs/orchestration/xyz/cli/README.md"
        ],
        "prompt": "Implement the CLI slice for XYZ. Read handoff_files first, work only in the CLI files named there, respect shared contracts, run focused verification, and return files changed, tests run, questions, risks, and next steps."

  ]
}

Example with two independent groups:
The assistant should emit two group tool calls in the same assistant message.

Tool call 1:
{
  "name": "feature-implementation",
  "description": "Agents implement feature XYZ.",
  "priority": "high",
  "calls": [...]
}

Tool call 2:
{
  "name": "branch-review",
  "description": "Agents review the branch, merge conflicts, and code quality.",
  "priority": "medium",
  "calls": [...]
}

Expected behavior:
- Group 1 returns when all implementation subtasks finish.
- Group 2 returns when all review subtasks finish.
- Whichever group finishes first is available first.
- If both complete in the same batch and ordering can be safely controlled, high priority comes before medium priority.
